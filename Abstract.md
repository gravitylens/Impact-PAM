# Lab Abstract

## Overview

This hands-on lab demonstrates how **CyberArk** secures privileged access to modern, hybrid environments using a **Zero-Standing-Privileges (ZSP)** and **Just-in-Time (JIT)** model. Working from a Windows workstation against a live AWS organization (EC2 Linux instances, an RDS PostgreSQL database, and Windows targets), you act as an end user who connects to cloud consoles, servers, and databases without holding any permanent standing access. Along the way you generate real session activity, trigger a threat-detection alert, secure an AI agent's access to data, and finally review the full audit trail of everything you did.

The lab shows both sides of the security story: how access is granted least-privilege and on-demand, and how every action is monitored, recorded, and audited.

## Key Products and Concepts

- **Secure Infrastructure Access (SIA)** – brokered, VPN-less, recorded access to Linux, Windows, and database targets
- **Secure Cloud Access (SCA)** – just-in-time elevation into cloud consoles (AWS) with zero standing privileges
- **Secure Web Sessions (SWS)** – browser-based session recording
- **Privilege Cloud** – credential vaulting and management (Personal Privileged Accounts)
- **Access space** – unified web portal for discovering and connecting to resources
- **Threat Detection and Response (TDR/ITDR)** – detection of suspicious in-session commands and automated response
- **AI Agents Gateway / MCP** – securing AI agent access to data with scoped, auditable, zero-standing permissions
- **Session Monitoring & Audit** – recordings, command audits, risk scoring, and AI-generated session summaries
- Core principles practiced throughout: **Zero-Standing Privileges**, **Just-in-Time elevation**, **Vaulted credentials**, **ephemeral accounts**, and **least privilege**

## What the Lab Includes

### Section 1 – Secure Access to Cloud-native Services and Elastic Workloads
Sign in to the workstation and the CyberArk Identity portal, then explore access to an AWS environment. You contrast connecting **directly** to the AWS console (which grants no standing access) against connecting with **SCA** just-in-time elevation. You then use **SIA/ZSP** to connect to a cloud-hosted Linux VM, attempt a connection to a second Linux VM that your policy does **not** permit (and are denied), and connect to a PostgreSQL database with an ephemeral, role-scoped user. Running a `passwd` command intentionally triggers activity that is detected later in the lab.

### Section 2 – Secure Access to Long-lived Windows Systems using ZSP
Connect to a long-lived Windows VM using zero-standing privileges, where SIA provisions an **ephemeral local user** (added to Remote Desktop Users) for the duration of the session and removes it afterward.

### Section 3 – Secure Standing Access to Long-lived Windows Systems
Onboard a **Personal Privileged Account (PPA)** into the Privilege Cloud Vault, then connect to a Windows target three ways: from the **Privilege Cloud** portal, from the **Access space**, and using **vaulted credentials with just-in-time elevation** — comparing standing access (vault-managed) against the lower-risk JIT model.

### Section 4 – Request Temporary Access to a Cloud Console
Use the **on-demand access request** workflow to request time-bound access to an AWS account you don't currently have, and watch it move through approval and automatic fulfillment/de-provisioning.

### Section 5 – Threat Detection and Response
Review the **Suspicious Activities in Sessions** alert generated by the earlier `passwd` command, inspect the configured detection pattern, the critical-severity security alert, the risky command details, and the automatic session-termination response.

### Section 6 – Secure AI Agents
Configure an AI assistant (Mistral **Le Chat**) with a **custom MCP connector** that authenticates to CyberArk via **OAuth 2.1** and reaches a database through the **Secure Infrastructure Access MCP server / AI Agents Gateway**. Using natural language, the agent lists and queries the database under scoped permissions, and is **blocked** from destructive actions (e.g., dropping a table) — demonstrating least privilege and zero standing privileges for AI agents, plus full auditability of agent activity.

### Section 7 – Review Session Recordings and Command Audit
Access the **Audit space** / Session Monitoring to review the activity generated throughout the lab: Windows, Linux, database, and AI-agent sessions — including video recordings, command audits, risk scores, and **CORA AI**-generated session summaries.

### Section 8 – Optional Exercise: Create and Run Alias Commands
Use a provided PowerShell script to create reusable **`cybr-ssh` / `cybr-sso`** connection aliases for SIA, simplifying repeat connections and leveraging **MFA caching** so repeat sessions don't require re-authentication.
